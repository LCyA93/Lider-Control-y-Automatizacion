## [v19.0.6.0.0] — Power BI Relational Modeling (Star Schema)

Date: 2026-10-21
Developer: Softhealer Technologies (via opencode)
Ticket: Client report — "Problem identified Power BI.docx" (relationships between `product.product` and `product.template`)

### Why
The client could not create any relationship between tables in Power BI. Every foreign key was exported as a readable name instead of its numeric record id, so no common key existed between the tables. The root cause was in the connector's relational flattening layer, not in Power BI and not in the `.mez` connector.

### What Changed

**`models/sh_models.py`**
* `_sh_powerbi_format_rows` now emits the numeric foreign key for Many2one fields and, in `id_and_display` mode, a companion `<field>_display` column with the readable name.
* `sh_powerbi_fetch_rows` switched from `read(fields, load=None)` to `read(fields)`, so both extraction endpoints return an identical payload shape (the previous mix produced `"194648"` as a display name).
* `sh_powerbi_search_read` now delegates to `_sh_powerbi_format_rows`, removing ~110 lines of duplicated flattening logic.
* Empty foreign keys return `None` (JSON null) instead of an empty string.
* `display_name` values that are `False` (records without a readable name) are normalised to an empty string.
* A companion column is never emitted when the model already owns a `<field>_display` field.
* `_sh_powerbi_get_relation_format` resolves the format from the target company, not `env.company`.
* `sh_powerbi_fetch_rows` now searches with `sudo()` so it returns the same rows and value types as `sh_powerbi_search_read`; access stays enforced through the company scoped Model Access allowlist and domain filter.

**`models/res_company.py`** / **`models/res_config_settings.py`** / **`views/res_config_settings.xml`**
* New `res.company.sh_powerbi_relation_format` setting with the three formats, exposed in Odoo Settings and in the Power BI Connector block.

**`models/sh_powerbi_push_config.py`**
* `_get_powerbi_field_groups` (new) returns the exposed fields as atomic `[base, companion]` groups and is the single source of truth for the schema, the row slicing and the counters.
* `_build_column_schema` is mode aware: `Int64` foreign keys for `id_and_display` / `id_only`, `String` for `display_only`, and the companion column only in `id_and_display`.
* `_build_powerbi_table_schemas` splits the 75 column limit by groups, so a foreign key and its companion never land in different part tables.
* `_get_qualified_schema_columns` / `_get_schema_diff` compare `table.column:dataType`, so a `String → Int64` change is detected. New `_sh_powerbi_type_only_drift` and `_sh_powerbi_split_drift` helpers.
* `action_push_model` recreates the dataset automatically for a background push instead of returning a wizard action that the cron silently discards.
* New `action_rebuild_all_datasets` action (exposed as the **Rebuild Datasets** button) to migrate existing datasets after a format change.

**`models/sh_powerbi_push_queue.py`**
* The model is bound to the configuration's owning company with `with_company()`, so the allowed fields, domain filter and relation format are always resolved against the target company.
* A type-only schema drift recreates the dataset and writes a `sh.powerbi.log` entry instead of raising.

**`models/sh_powerbi_model_access.py`**
* `_compute_powerbi_table_stats` now reuses the push side field builder, so the reported column and table counts match the dataset that is really created.

**`models/sh_powerbi_schema_diff_wizard.py`**
* The diff is split into Added, Removed and **Changed Column Types**; a type change is marked destructive and is no longer double counted.

### Tests
* New `tests/test_sh_powerbi_relationships.py` with 21 cases covering the PK-FK relationship, accounting / inventory / purchase / sales flows, null handling, the three relation formats, the push schema of each mode, row slicing, type aware drift detection, split table adjacency, the display name collision guard, multi company isolation, the background drift path, the counters and endpoint parity.
* `tests/test_powerbi_relationships.py` removed, `tests/__init__.py` updated.

### Verification
* `sh_integration_base_19`: **21 tests, 0 failed, 0 errors**.
* Live sweep over the 392 registered models in the database: **254 models verified with zero relational integrity errors in all three relation formats**. The 3 remaining models raise on purpose inside Odoo core (`account.root`, `account.code.mapping`) or have no table (`website.technical.page`).

### Side Effects
* Existing Power BI Desktop reports that used the readable name in a foreign key column must set **Change Type → Whole Number** on those columns after the first refresh.
* Existing push datasets must be recreated (Power BI cannot alter a column type in place). Use the **Rebuild Datasets** button, or let the background push recreate them automatically.
* `sh_powerbi_fetch_rows` now returns the same rows as `sh_powerbi_search_read`; record rules are no longer applied on that endpoint because access is enforced through the company scoped Model Access configuration.
